TWO IDEAS CARRY THE WHOLE DESIGN. (1) SCOPE: a module recipe addresses columns by ObjectId; a WORKSPACE recipe has module:null, runs on every module, and addresses them by NAME (`columnName`), resolved per-event against the module the event happened on — an id there would silently narrow it back to one board, which is what the user chose workspace scope to avoid. The two addressing modes are never mixed and scope is FIXED at creation (updateAutomation reads scope from the STORED doc, never the body). (2) SUBJECT: subjectOf(triggerType) in services/automation/triggers.ts says whether a trigger is about a record or a sub-record, and the engine drops any event whose subject disagrees. That is what keeps "when a record is created" off checklist lines now that sub-records DO reach the engine — the old blanket `if (parentRecord) return` is gone. ENGINE SPLIT into services/automation/: index.ts (orchestrator), triggers.ts, conditions.ts, columns.ts (ColumnResolver, per-request name->id cache, anchored+ESCAPED regex), values.ts (str/same/asNumber/fillTemplate), recipe.ts (sanitise+validate, shared with the controller so the two cannot disagree), emit.ts, and actions/{record,subrecord,parent,create}.actions.ts + writeCell.ts behind a HANDLERS registry — nothing switches on action type any more, so an unknown type is skipped rather than throwing. services/automation.service.ts is now a 2-line RE-EXPORT SHIM so every existing import keeps resolving. Unchanged invariants: `void runAutomations(...)` (never awaited), no cascades (actions write models directly), errors land on lastError, activity attributed to the TRIGGERING user with metadata.automation. Every action returns false when the record is already in the requested state — that is what keeps the run feed honest and stops a recipe pointed at its own trigger column from looping. Action `value` supports exactly two placeholders, {record} and {value} (fillTemplate) — richer ones need a resolver with its own failure modes. EMITTERS: emitColumnChange() does ONE parentRecord lookup then fires the correct record-vs-subrecord trigger PAIR (firing all four would double the hot path); emitIfChecklistFinished() decides all_subrecords_completed against the DB after the write, and refuses to fire when the count is zero (a record with no sub-records has not "completed them all"). Atlas delete flow: history reaches the model as PLAIN TEXT (tool_use/tool_result blocks are never replayed), so after 'do you want to delete X?' -> 'yes' the id from the previous turn is GONE. delete_item therefore accepts an id OR an exact name and resolves it via resolveTargetId() — workspace by name across the user's memberships, module by name within context.workspaceId, collection/record/column by name within context.moduleId. Atlas authorisation: NEEDS_AUTHORISATION in agentTools.service.ts = {delete_entity, create_workspace, create_module} — deletes plus the two STRUCTURAL creations. Collections/records/columns/values stay immediate; gating the everyday flow would make the agent tedious rather than safe. Atlas confirmation, the prompt half: the system prompt must say 'Never ask permission in words. Call the tool — the app shows an Authorise button.' SAFETY RULE (learned the hard way 2026-08-25): authorisation must NEVER be a field on a tool's input schema. `confirm: {type:"boolean"}` was in delete_entity's schema, so the model simply set confirm:true itself and deleted six collections with no button ever shown — anything in a schema is something the model can and will set. It is now an ExecuteOptions ARGUMENT on executeTool(name, input, context, {authorised}), settable only by server code: runAuthorised() (the /confirm route, after a real press) and the batch loop recursing into its own single-item path. runAgent additionally strips any `confirm` the model invents before executing, and the pending payload sent to the client is stripped of confirm/authorised so it can never re-arm anything. Regression test lives in the transcript: forge confirm:true on delete_entity (single AND batch) plus create_workspace/create_module and assert needs_confirmation with nothing applied.
Blueprint (one-press setup): services/blueprint.service.ts + the create_blueprint tool.
